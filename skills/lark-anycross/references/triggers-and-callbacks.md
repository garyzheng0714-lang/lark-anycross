# 触发器与回调

## 网址触发器

- 鉴权只有「无鉴权」和 Basic（账户名加密码），外加 IP 白名单。默认是无鉴权（`authorization_method=0`），知道地址就能触发。（实测）
- IP 白名单多个用英文分号隔开，不支持 CIDR 网段。（文档；白名单生效是实测）
- 验不了自定义签名。外部系统发来带签名的请求，只能靠 IP 白名单把关，或先经自己的服务验签再转发。
- 从白名单外调用返回 403（`code: 7`）。本机调不通、换到白名单里的服务器就 200。排错时先确认调用方 IP。（实测）
- 由多维表格自动化调用时，Basic 密码和地址写在一起，能看到自动化的人都看得到。这时更有用的是收紧谁能看这个自动化和项目。由服务端调用时，用 IP 白名单，或者把 Basic 密码放进服务端环境变量。
- 回调地址就是密钥。不写进文档、代码、Git、聊天。接新项目时从服务器已有的环境文件里复制，测试脚本从环境变量取，日志只打 HTTP 状态码。
- 想知道是谁在调，看节点日志里触发器出参的 `headers`。多维表格自动化发来的请求带 `X-Base-Automation-Ua: automation/1.0.0`，`User-Agent` 是 `Go-http-client/2.0`，按记录调时参数放在 query 里（例如 `record_id`）。输出时去掉 `Host`、`X-Rewrite-Url`（里面就是回调地址）和 `X-Tt-Logid`。（实测，2026-11-12）
- 多维表格按记录调的流程，查不到、出错时也要把状态写回那条记录。不写的话，记录一直是「待处理」，下一次批量跑又会把它送进来。接的是按次收费的接口时，钱会反复花在同一批查不到的记录上。曾有一条这样的流程 3 个多小时跑了 5.7 万次、失败 4.4 万次；抽样里在后面几批重复出现的记录，前一次全是失败。（现象实测；自动化怎么挑记录没看到，是推断）

## 异步和同步

- 异步触发器收到就回 HTTP 200，内容 `{"code":"0","message":"success"}`。这只说明收到了，不说明跑了。看运行日志确认。（实测）
- 同步触发器的超时可设 1 到 60000 毫秒，默认 10000。超时后流程仍会跑完，只是调用方拿不到结果。同步返回内容上限 256KB，超了会截断并让节点失败。（文档）
- 同步触发器的草稿地址在发布之前返回 404。（实测）
- 触发器出参里 query 的子字段要手动声明，下游才能引用。（实测）
- 同步回调的响应头只能从 10 个白名单头里选，没有 Location、Set-Cookie，也设不了 CORS。浏览器基本没法直接调，也做不了登录中心。（文档）

## 分支条件

照分支条件的真实写法拼请求，先看条件到底比较的是哪个字段。

分支前面的 HTTP 节点要是还用默认错误处理「重试，还失败就终止」，对方一回非 2xx（例如「查询无结果」），整次运行就停在这一步，后面专门处理这种情况的分支一次也走不到。要让分支接住，把错误处理改成「重试，还失败走分支」或「忽略」。分支比的字段也要对上：失败时平台的错误信息 `code` 是 `555`，对方自己的业务码（例如 `50002`）在节点出参的 `error_code` 里。拿 `error_code` 去比 555，永远不成立。（默认处理会终止是实测；改成忽略以后出参长什么样没验证过，改之前先调试一次，看清出参再写条件。）

条件是「整个 body 等于 `prod`」时，请求体必须就是 JSON 字符串 `"prod"`，并带 `Content-Type: application/json`。`{"env":"prod"}`、纯文本 prod、query 参数都会落进默认分支。曾经试了 10 种写法都拿到同一个测试环境的 token，看了分支条件截图才找到原因。写入生产之前，先用一个只读接口确认拿到的东西对正式环境有效。（实测）

```sh
curl -sS -o /dev/null -w '%{http_code}\n' -X POST "$ANYCROSS_CALLBACK_URL" \
  -H 'Content-Type: application/json' --data '"prod"'
```

## 定时触发器

- 最长有效两年，自定义生效期也一样。到期前要重新发布，否则静默停跑。把到期日记进台账。（实测）
- 调试时报「服务内部错误」，原因是调试输入里的时间戳是 0。把 `{"timestamp": <当前毫秒>}` 粘进调试输入就能跑。（实测）
- 时间按 UTC 计算。
- 会静默停跑。2026-11-03 到 11-10，同一个项目的 4 条「每 10 分钟」定时停了 7～8 天：不是到期，没有失败记录，告警抓不到，后来各自在不同时间恢复，原因没查到。同期别的项目的定时（每 30 分钟、每 70 分钟、每天）一次没漏，这 4 条在 10-24 凌晨还各漏过一次。所以定时流程不能只靠失败告警，要另有东西盯着「该跑没跑」。（实测）

## 无限触发（自己调自己）

- 意思是一轮跑完、插一段缓冲（比如等 10 分钟）、再调自己的回调地址开下一轮。节奏跟着运行时长走，不是固定节拍。用一条流程每 15 分钟叫一次同步，被用户否掉了：一轮比一拍长时会叠着跑。（用户定，2026-11-12）
- 老写法中间失败一次链就断了，实测两次各断了 16～17 小时：一次是鉴权连接超时，一次是接口回空列表让计数节点报错。
- 改进写法见 [配方：无限触发的增量同步](guide/guides/RECIPES.md)。要点有五个：
  - 接力号放在网址参数里传，拉起时换新号，老链对不上号自己结束，同时只留一条链。
  - 一棒只做几页，没做完马上接着做；一轮做完才同步调用「等 10 分钟」子流程。
  - 取数据出错走分支，等 1 分钟再取，最多 30 次。
  - 失败了，告警流程前两次马上拉起。
  - 静默断了，每小时一次的定时「看门」流程拉起。

  （搭好并校验，2026-11-12，未实跑）
- 等待只能靠 While 加延迟节点（单个最长 3 秒）。老流程的等待子流程每圈 2.6 秒，等 10 分钟约 200 圈。

## 手动触发器

只能在「调试」里运行，不能发布。在编辑页填好输入，点「调试」。用完把输入框清空再保存，免得别人误点。（文档加实测）

## 飞书事件触发器

同一个飞书应用的事件只交给一个接收方。服务端已经用长连接收这个应用的事件，就别在集成平台给同一应用配事件触发器，否则事件会被两边分走、两边都漏。正确做法是服务端收到后转发到网址触发器。（文档加推断）
